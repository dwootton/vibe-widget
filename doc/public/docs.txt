# Installation
URL: https://vibewidget.dev/docs
Install the package, set one API key, and create a first widget.
Vibe Widget runs on Python 3.9 or newer, and it needs one API key to generate a widget. Widgets that were generated earlier and cached on disk open without a key. pip install vibe-widget 1. Add a key Create a .env file next to your notebook holding any one of these lines: ANTHROPIC_API_KEY=sk-ant-... OPENAI_API_KEY=sk-... OPENROUTER_API_KEY=sk-or-... Vibe Widget reads the .env file, picks the provider that matches the variable name, and uses that provider&#x27;s default model. Nothing else needs to be set. Exporting the same variable in your shell works the same way, and a value already in the environment is never overwritten by the file. You can get a key from Anthropic, OpenAI or OpenRouter. One OpenRouter key reaches models from every vendor. 2. Create a widget Widget PreviewOpen the live docs to see this interactive widget. import pandas as pd import vibe_widget as vw df = pd.read_csv(&quot;sales.csv&quot;) widget = vw.create(&quot;bar chart of revenue by region&quot;, df) widget To see what was picked up, call vw.config() with no arguments: vw.config() # Config(provider=&#x27;anthropic&#x27;, host=&#x27;api.anthropic.com&#x27;, model=&#x27;claude-opus-5&#x27;, # key_source=&#x27;ANTHROPIC_API_KEY (/work/analysis/.env)&#x27;, environment=&#x27;vscode-like&#x27;, ...) The output names the variable and file the key came from, and never prints the key itself. Where it runs The same two steps work in every supported host. JupyterLab and Jupyter Notebook need nothing extra. VS Code notebooks get React bundled into each widget, because VS Code has no import maps. Positron is handled the same way as VS Code, and is detected through POSITRON rather than VSCODE_PID. Google Colab generates code synchronously, because background threads break widget updates there. Quarto works in .qmd documents rendered with the Jupyter engine. Put the .env file in the project directory. Opening a widget someone else generated Generated code is written to .vibewidget/ in your project, and the folder can be committed to git. A collaborator who clones the repository can open those widgets with no API key at all, because loading cached code makes no model call. A key is needed again only when someone generates, edits, audits, or repairs a widget. Brush selection example Widget PreviewOpen the live docs to see this interactive widget. import pandas as pd import vibe_widget as vw df = pd.read_csv(&quot;sales.csv&quot;) widget = vw.create( &quot;scatter plot with brush selection, and a linked histogram&quot;, df, outputs=vw.outputs(selected_indices=&quot;indices of selected points&quot;) ) widget For help setting API keys inside Jupyter, see this guide.


# Configuration
URL: https://vibewidget.dev/docs/config
Set the model, the endpoint, and the safety limits.
vw.config() reads and changes the settings every widget uses. Called with no arguments it reports what is currently in effect, and called with keyword arguments it changes those settings for the rest of the session. import vibe_widget as vw vw.config(model=&quot;claude-sonnet-5&quot;) vw.config(mode=&quot;premium&quot;) vw.config(execution=&quot;approve&quot;) API key setup Put one key in a .env file next to your notebook: ANTHROPIC_API_KEY=sk-ant-... OPENAI_API_KEY=sk-... OPENROUTER_API_KEY=sk-or-... The file is looked for in the working directory and each parent directory, stopping at the repository root or your home directory. A variable already present in the environment is never overwritten, so an exported value wins over the file. No extra package is needed, and you should not call dotenv.load_dotenv() yourself. Exporting the variable works the same way: export ANTHROPIC_API_KEY=&#x27;your-key&#x27; $env:ANTHROPIC_API_KEY=&quot;your-key&quot; Keep keys out of the notebook itself, because a hardcoded key is easy to commit or share by accident. Provider inference When you do not set base_url, the key you supplied decides both the endpoint and the default model. VariableEndpointDefault modelVIBE_API_KEYVIBE_BASE_URL, or OpenRouterdepends on the endpointANTHROPIC_API_KEYhttps://api.anthropic.com/v1/claude-opus-5OPENAI_API_KEYhttps://api.openai.com/v1gpt-5.5OPENROUTER_API_KEYhttps://openrouter.ai/api/v1google/gemini-3-flash-preview The variables are checked in that order, so VIBE_API_KEY overrides everything and OPENROUTER_API_KEY is the last one tried. An explicit vw.config(api_key=...) beats all of them. When a key carries a prefix belonging to a different vendor, such as an sk-ant- value stored in OPENAI_API_KEY, the variable name decides the provider and a warning is printed once. Calling vw.config() with no arguments reports what was inferred, without printing the key: vw.config() # Config(provider=&#x27;openai&#x27;, host=&#x27;api.openai.com&#x27;, model=&#x27;gpt-5.5&#x27;, # key_source=&#x27;OPENAI_API_KEY (/work/analysis/.env)&#x27;, environment=&#x27;quarto&#x27;, ...) provider is derived from the endpoint and reads anthropic, openai, openrouter or custom. environment lists the notebook hosts detected for the running kernel, such as vscode-like for VS Code and Positron, quarto, colab or pyodide. Changing only the model keeps the provider your key selected: vw.config(model=&quot;claude-sonnet-5&quot;) # still Anthropic A model id written in OpenRouter&#x27;s vendor/name form is routed to OpenRouter when OPENROUTER_API_KEY is set, even if an Anthropic or OpenAI key is also present, because that form of id exists only on OpenRouter. Going back to a plain model name returns you to the provider your other key selects. vw.config(model=&quot;anthropic/claude-opus-4.5&quot;) # OpenRouter, when its key is set vw.config(model=&quot;claude-sonnet-5&quot;) # back to Anthropic Without an OpenRouter key the same id raises a ValueError explaining that Anthropic&#x27;s own API does not know the name, and telling you to use the plain name or point base_url at OpenRouter. Endpoint Set base_url to reach any other OpenAI-compatible server, including one running on your machine. vw.config(base_url=&quot;http://localhost:11434/v1&quot;, model=&quot;qwen2.5-coder&quot;) # Ollama vw.config(base_url=&quot;http://localhost:8000/v1&quot;, model=&quot;Qwen/Qwen2.5-Coder-32B&quot;) # vLLM An endpoint on localhost, 127.0.0.1 or ::1 needs no API key, because local servers ignore it. Set VIBE_API_KEY anyway when yours sits behind an auth proxy. For an endpoint with no dedicated variable, such as Azure OpenAI, set both VIBE_API_KEY and VIBE_BASE_URL: VIBE_API_KEY=your-key VIBE_BASE_URL=https://my-resource.openai.azure.com/openai/v1 Requests adapt to what the endpoint accepts. Newer OpenAI models want max_completion_tokens instead of max_tokens, and some models reject temperature outright. The rejected parameter is renamed or dropped and the correction is remembered, so only the first call to a given endpoint pays for it. timeout is the HTTP timeout in seconds for one model call, and it defaults to 120. Raise it for slow local models. vw.config(timeout=300.0) Models and modes vw.models prints the catalog, and vw.models.standard and vw.models.premium return the default id for each tier. vw.models vw.models.standard # &quot;google/gemini-3-flash-preview&quot; vw.models.premium # &quot;google/gemini-3-pro-preview&quot; mode picks between two OpenRouter defaults, a faster and cheaper one and a slower and stronger one. vw.config(mode=&quot;standard&quot;) # google/gemini-3-flash-preview, the default vw.config(mode=&quot;premium&quot;) # google/gemini-3-pro-preview Setting mode swaps the model only while you are on one of those two defaults. Once you name a model yourself, your choice stays, and mode no longer changes it. The word &quot;openrouter&quot; can be passed as the model name to mean whichever id the current mode points to. vw.config(mode=&quot;premium&quot;, model=&quot;openrouter&quot;) # google/gemini-3-pro-preview Common options vw.config( execution=&quot;auto&quot;, # &quot;auto&quot; or &quot;approve&quot; retry=2, # automatic repair attempts per generation agent_preset=&quot;project&quot;, agent_run={&quot;permission_tier&quot;: 1, &quot;allowed_roots&quot;: [&quot;.&quot;]}, bypass_row_guard=False, base_url=None, # None means infer from whichever API key is set timeout=120.0, # HTTP timeout, seconds data_privacy=&quot;sample&quot;, # &quot;sample&quot; or &quot;schema&quot; sample_rows=3, # rows sent per input in &quot;sample&quot; mode ) The three settings that take fixed strings also have namespaces, so you can let autocomplete fill them in: vw.execution.auto, vw.execution.approve, vw.mode.standard, vw.mode.premium, vw.presets.safe, vw.presets.project and vw.presets.connected. Automatic repair When generated code throws an error in the browser, the error is sent back to the model and the model is asked to fix it. retry is how many of those attempts one generation is allowed. vw.config(retry=2) # the default vw.config(retry=0) # never repair automatically The budget covers a single generation. A repair that succeeds does not refill it, so a widget that keeps failing cannot loop indefinitely, and a new generation starts with a full budget again. Once the attempts are used up the widget&#x27;s status becomes blocked, and a log line tells you to describe the fix in the prompt box or to raise the budget with vw.config(retry=N). Typing a fix into the prompt box still works at retry=0, because the budget only governs the automatic attempts. Cost Each widget counts the tokens it spent: widget.usage # {&#x27;prompt_tokens&#x27;: 18432, &#x27;completion_tokens&#x27;: 5120, &#x27;requests&#x27;: 2} Loading a cached widget makes no request, so the counts stay at zero until something calls the model. With no API key set there is no provider at all, and widget.usage is an empty dict. Safety and permissions Generated code runs in the notebook page with the same privileges as the page. It can reach the DOM, cookies and localStorage for the notebook origin, and any network endpoint the browser is allowed to call. There is no browser-level sandbox around it. Execution mode execution decides whether generated code runs as soon as it arrives or waits for you. vw.config(execution=&quot;approve&quot;) # review the code before it runs vw.config(execution=&quot;auto&quot;) # run immediately, the default In &quot;approve&quot; mode the code does not execute until you approve it. Approval is decided in Python rather than in the browser, so a widget cannot approve itself. The widget stores a hash of the code you approved, and if the code changes through an edit or a repair the approval resets and you are asked again. Agent presets An agent preset decides which tools the model is allowed to call while it works. PresetPermission tierFile accessNetworkUse case&quot;safe&quot;0 (read-only)Sandbox onlyNoSensitive data, minimal risk&quot;project&quot;1 (read-write)Working dir + sandboxNoGeneral use (default)&quot;connected&quot;2 (full)Working dir + sandboxHTTPS onlyFetching remote data vw.config(agent_preset=&quot;safe&quot;) # read-only tools, sandboxed vw.config(agent_preset=&quot;project&quot;) # read-write in your project directory, the default vw.config(agent_preset=&quot;connected&quot;) # also allowed to fetch HTTPS URLs Tier 0 tools are data.profile, fs.list, fs.read, fs.exists, fs.glob, state.get, state.put and pls.describe. Tier 1 adds data.load, fs.write, fs.mkdir and fs.read_base64. Tier 2 adds net.fetch, restricted to HTTPS with an allowlist for hosts and MIME types, and it requires allow_net_fetch. Row guard An input of more than 100,000 rows raises a ValueError naming the row count, so that a large frame cannot exhaust memory while it is being prepared for the widget. vw.config(bypass_row_guard=False) # keep the guard, the default vw.config(bypass_row_guard=True) # allow larger datasets A locked-down configuration For sensitive data or a shared machine, the settings below turn off everything that acts on its own: vw.config( execution=&quot;approve&quot;, # require manual approval agent_preset=&quot;safe&quot;, # read-only tools, sandboxed bypass_row_guard=False, # enforce the row limit retry=0, # no automatic code repairs ) What is sent to the model provider Vibe Widget sends the following: your prompt and theme prompt a schema summary of each input, covering shape, column names, dtypes, null counts, cardinality, and numeric min, max and mean the first sample_rows rows of each input, 3 by default, when data_privacy is &quot;sample&quot; the declared inputs, outputs and actions the full widget code for edits, audits, and runtime repairs runtime error messages, when a repair is running Controlling what leaves the notebook data_privacy chooses between the two summary modes. vw.config(data_privacy=&quot;schema&quot;) # schema only, no cell values vw.config(data_privacy=&quot;sample&quot;) # schema plus head rows, the default vw.config(sample_rows=1) # fewer rows in &quot;sample&quot; mode In &quot;schema&quot; mode the summary carries no cell values at all, so there are no head rows, no category examples and no sampled values. Only the shape and the per-column description are sent. Inputs that are not tables are summarized by type and length, and their truncated repr is included in &quot;sample&quot; mode only. data_privacy governs the summary built from the values you pass to vw.create. It does not restrict the agent&#x27;s data.profile tool, which reads sample values from any file it is allowed to open. Combine data_privacy=&quot;schema&quot; with agent_preset=&quot;safe&quot; to keep the agent out of your project directory as well. No API keys are written to disk. Generated widgets and audit reports are stored locally under .vibewidget/. When a request fails A failed model call raises a ProviderError carrying a short explanation instead of the raw SDK exception. Each error names its kind, which is one of auth, quota, not_found, rate_limit, connection, timeout, context_length or other. A quota error means the key itself is valid but its spending limit is used up, which is worth separating from auth, because rotating a working key does not help. For quota and not_found the provider&#x27;s own sentence is passed through, since it usually names the exact limit or model, and the raw response body is never included.


# Create
URL: https://vibewidget.dev/docs/create
Generate a widget from a prompt and a dataset.
vw.create sends your prompt and a summary of your data to a model, and the model writes the JavaScript that draws the widget. The generated code is stored in .vibewidget/ in your project, so the next call with the same prompt and the same data reuses it instead of paying for a second model call. Widget PreviewOpen the live docs to see this interactive widget. import vibe_widget as vw widget = vw.create( &quot;bar chart of revenue by region&quot;, df ) widget The second argument accepts a pandas DataFrame, a path to a data file, a URL, or a directory to search. Recognized file types include CSV, TSV, JSON, GeoJSON, Parquet, NetCDF, XML, Excel, PDF, and plain text. You can leave the argument out when the widget does not read a dataset. When the cache is reused The stored code is found again by a key built from your prompt, the column names and dtypes of the data, the declared inputs and outputs, and the theme description. Changing any one of them produces a different key, so the model is called again and the earlier widget stays on disk. Row counts are deliberately left out of the key, so appending rows to a DataFrame reuses the widget you already have. Pass cache=False to force a fresh generation, and use vw.clear() to delete stored widgets. Themes A theme is a description of how the widget should look, written in plain language, and the model follows it while generating the code. vw.create(&quot;...&quot;, df, theme=&quot;financial_times&quot;) vw.themes() lists the built-in names. To write your own, see Theming. Inputs, outputs, and actions Values can flow into a widget from Python, out of a widget back to Python, and from Python as one-time commands. For the full model and worked examples, see Reactivity. What the generated code can do Generated JavaScript runs in the notebook page with the same privileges the page has, so it can reach the DOM, storage for the notebook origin, and any network address the browser allows. There is no browser sandbox around it. Read a generated widget the way you would read a script a stranger sent you, and use vw.config(execution=&quot;approve&quot;) when you want to see the code before it runs.


# Edit
URL: https://vibewidget.dev/docs/edit
Change a generated widget with a follow-up prompt, in Python or in the widget itself.
widget.edit(...) describes a change in plain language and returns a new widget with that change applied. The existing code goes to the model along with your instruction, so the model revises what is there rather than starting over, and the parts you did not mention stay as they were. chart = vw.create(&quot;scatter plot of price against mileage&quot;, df) v2 = chart.edit(&quot;add hover tooltips and a right-side legend&quot;) An edit keeps the theme of the widget it came from, along with its prompt history, so the look stays consistent while you change behavior. Inputs, outputs and actions are not carried over, so declare again any that the new version still needs. To change the look at the same time, pass a different theme: v3 = v2.edit(&quot;soften the palette and reduce gridlines&quot;, theme=&quot;minimal&quot;) vw.edit(description, source) does the same thing when you would rather name the source explicitly, and the source can be a widget, a handle, or a path to a saved .vw file. Editing one component A generated widget is often made of several pieces, and you can list them and work on one at a time. widget.components # [&#x27;scatter_chart&#x27;, &#x27;color_legend&#x27;, &#x27;slider&#x27;] widget.component.color_legend # renders on its own widget.component.color_legend.edit(&quot;use a horizontal layout&quot;) Each entry in widget.component is a widget in its own right, so it has the same edit and save methods as the whole thing, and it renders when it is the last expression in a cell. Editing inside the widget Every rendered widget has an editor. Opening it shows the generated code, a prompt box for the next change, and the audit findings when an audit has been run. An edit made in the editor updates the same widget in place, and the new code is stored in .vibewidget/ the way a generated widget is. In approve mode the editor is also where you read the code and approve it, so nothing runs until you have seen it. Reading the history Every prompt that shaped a widget is kept in order, which is useful when a widget has been through several rounds and you want to know how it got there. widget.prompt_history Cost An edit is a model call, so it is billed like a generation. Reruns with new data are not, because they reuse the code that already exists. See Reactivity for reruns, and Theming for keeping a consistent look across edits.


# Audit
URL: https://vibewidget.dev/docs/audit
Ask a second model call to review a generated widget and report what it finds.
An audit is a second model call that reads the generated code and writes up what it notices. The findings are that model&#x27;s opinion. No static analysis runs behind them, and the package never consults an audit before code executes, so an audit reads like a colleague&#x27;s comments on a pull request. To gate execution on your own reading of the code, use vw.config(execution=&quot;approve&quot;). Running an audit report = widget.audit(level=&quot;fast&quot;, display=False) full_report = widget.audit(level=&quot;full&quot;, reuse=True, display=False) A fast audit is a quick scan meant for early iteration, and a full audit covers more ground and suggests alternatives for the choices it flags. reuse=True returns the stored report when the code has not changed since the last audit, instead of paying for another call. Audits never run on their own. Nothing is sent to the model until you call widget.audit(...) or press the audit button in the widget&#x27;s editor. What the report covers Each finding is filed under one of four areas of the widget. AreaWhat it coversDataSelection, transformation, format, provenanceComputationMethod, parameters, assumptions, executionPresentationEncoding, scale, compression, framingInteractionTriggers, state, propagation, feedback A finding is scoped with an id such as data.transformation.date_parsing, and it carries the line numbers in the generated code that it refers to, so you can go straight to the place it describes. The seven lenses In a full audit every finding is also rated along seven fixed lenses, which is what makes one finding comparable to another. A fast audit reports findings without them. Impact, rated high, medium or low, answers whether a different choice would change the conclusions a reader draws. Uncertainty covers confidence, sample size and stability. Reproducibility asks whether the result can be recreated exactly. Edge behavior covers empty, extreme and boundary inputs. Default vs explicit separates a choice you made from an assumption the model made for you. Appropriateness asks whether the method suits the question. Safety covers network calls, dynamic code execution, writes to storage, cross-origin fetches, and injected scripts or iframes. The model is told to keep high impact rare and to default to low unless there is clear evidence, so most reports come back full of low-impact findings. Where reports are stored Reports are written to .vibewidget/audits/ as JSON and YAML. The directory is listed in .vibewidget/.gitignore, so reports stay on the machine that ran them rather than going into your repository. Working from an audit In the widget&#x27;s editor, findings are shown as a checklist next to the code. You can turn any one of them into an edit request, which sends the finding back to the model as the instruction for a fix, or leave it on the list as a note for later.


# Reactivity
URL: https://vibewidget.dev/docs/reactivity
Send values into a widget, read values back out, and link widgets together.
Values move between Python and a widget in three ways. An input carries a value from Python into the widget and stays set. An output carries a value from the widget back to Python and also stays set. An action sends a one-time command from Python to the widget and leaves nothing behind. PrimitiveDirectionPersistenceUse forInputPython to JSState, stickyData, configuration, selections from other widgetsOutputJS to PythonState, stickyUser selections, computed values, filtersActionPython to JSEvent, fires onceCommands such as reset, focus, export Inputs You declare inputs when you create the widget, either with vw.inputs(...) or with a plain dict. An input keeps its value until you change it. chart = vw.create( &quot;scatter plot that dims points below the threshold&quot;, df, inputs=vw.inputs(df, threshold=0.5), ) vw.inputs() takes keyword arguments and bare positional values. A positional value is named after the variable you passed, so vw.inputs(df, threshold=0.5) declares inputs called df and threshold. Every declared input becomes a synced trait on the widget, so assigning a new value updates the widget without regenerating any code: chart.threshold = 0.8 Direct assignment sends the value as it is, so it expects something JSON-friendly, meaning numbers, strings, booleans, lists and dicts. NumPy arrays, NumPy scalars and timestamps are converted for you when the widget is created but not on later assignment, so run them through the same helper: from vibe_widget.utils.serialization import clean_for_json chart.frame = clean_for_json(numpy_array) To swap the underlying dataset, rerun the widget instead of assigning to an input. Rerunning with new data vw.create returns a handle, and calling that handle runs the same generated code against different data or inputs, with no second model call: chart = vw.create(&quot;scatter plot with brush selection&quot;, df) chart(new_df) # same widget, different data chart(vw.inputs(threshold=0.7)) # merges with the inputs already declared chart(inputs={&quot;threshold&quot;: 0.7}) # replaces the declared inputs A positional vw.inputs(...) bundle merges into the inputs the widget was created with, while the inputs= keyword replaces them. When the new dataset is missing a column the widget was built against, the rerun raises a ValueError naming the missing columns rather than drawing a broken chart. Outputs An output carries a value the widget produced back to Python, and like an input it keeps its value. # Read the current selection print(widget.outputs.selected_indices.value) # React to changes def on_selection(change): print(f&quot;Selection changed: {change.new}&quot;) widget.outputs.selected_indices.observe(on_selection) # Stop listening widget.outputs.selected_indices.unobserve(on_selection) The handler receives the traitlets change object, which carries new, old, name and owner. Actions An action is a one-time command from Python to the widget, for behavior that should happen once rather than persist as state. Widget PreviewOpen the live docs to see this interactive widget. widget = vw.create( &quot;interactive scatter plot&quot;, df, actions=vw.actions(reset_view=&quot;Reset zoom and pan&quot;) ) widget.actions.reset_view() Once an action fires it is finished, and the widget holds no record that it was reset. Choosing between them Ask whether the value should stick around. When it should, use an input if the value comes from Python and an output if it comes from the widget. When it should not, use an action. Modelling a one-time command as an input makes it sticky, which is usually wrong: # Avoid this widget.should_reset = True The widget would reset and then keep resetting, because the input is still true. An action fires once and leaves nothing set, which avoids the problem. Linking widgets together To connect two widgets, pass one widget&#x27;s output as another widget&#x27;s input. Widget PreviewOpen the live docs to see this interactive widget. scatter = vw.create( &quot;scatter plot with brush selection tool&quot;, df, outputs=vw.outputs(selected_indices=&quot;indices of selected points&quot;) ) histogram = vw.create( &quot;histogram with highlighted bars for selected data&quot;, vw.inputs(df, selected_indices=scatter.outputs.selected_indices) ) Selecting points in the scatter plot updates the histogram through trait syncing. Nothing reruns and no model call happens, because the link is a Python observer on the source output that writes straight into the target input. A link runs one way, from the named output to the named input. To link in both directions, declare an output on each widget and an input on the other.


# Load & Save
URL: https://vibewidget.dev/docs/composability
Store widgets on disk, share them through git, and reload them later.
A widget can be written to a single portable file, and generated code is also kept in your project so that a later call reuses it. Both let you come back to a widget without paying for another model call. Save a widget Widget PreviewOpen the live docs to see this interactive widget. widget = vw.create(&quot;scatter plot with brush selection&quot;, df) widget.save(&quot;my_widget.vw&quot;) To store the input values alongside the code, so the widget reloads showing the same state: widget.save(&quot;my_widget_with_inputs.vw&quot;, include_inputs=True) A .vw bundle holds the widget code, its metadata, and the signatures of its inputs and outputs. With include_inputs=True the input values are embedded as well. Load a widget loaded = vw.load(&quot;my_widget.vw&quot;) loaded Loading uses approval mode by default, so you can read the code before it runs: loaded = vw.load(&quot;my_widget.vw&quot;, approval=True) For a file you trust and want to run straight away: loaded = vw.load(&quot;my_widget.vw&quot;, approval=False) Calling vw.load() with no path opens a selector listing the widgets cached in your project. Sharing through git Generated code is stored under .vibewidget/ in your project, as one .js file and one .json sidecar per widget. Commit .vibewidget/widgets/ and a collaborator who clones the repository gets your widgets with it. Opening one of them makes no model call, so a collaborator needs no API key until they generate, edit, or audit something themselves. Audit reports are written to .vibewidget/audits/, which is listed in .vibewidget/.gitignore, so reports stay on the machine that produced them. Clearing what is stored vw.clear() deletes cached widgets and audit reports, forgets the themes generated this session, and returns a count of what it removed. vw.clear() # everything vw.clear(&quot;widgets&quot;) # generated widget code only vw.clear(&quot;audits&quot;) # audit reports only vw.clear(&quot;themes&quot;) # forget themes generated this session vw.clear(widget) # just that widget&#x27;s code and audits vw.clear(&quot;sales_chart&quot;) # the same, by variable name Themes you saved with Theme.save are files in .vibewidget/themes/ and are not removed by vw.clear. Delete the file when you want one gone for good. Before you run a file someone sent you A loaded widget executes JavaScript in your notebook with the privileges of the notebook page. Keep approval=True for any file you did not generate yourself, and read the code before approving it.


# Theming
URL: https://vibewidget.dev/docs/theming
Describe how a widget should look, and reuse that description across widgets.
A theme is a description of how a widget should look, written in plain language. The description goes into the prompt, so the colours, type and spacing end up written into the generated JavaScript itself. There is no stylesheet layered on afterwards, and changing a theme means generating again. Listing the built-in themes import vibe_widget as vw vw.themes() In a notebook vw.themes() prints a short list. To get the underlying dict, use dict(vw.themes()). Using a theme Pass the name of a built-in theme: vw.create(&quot;...&quot;, df, theme=&quot;financial_times&quot;) A string that is not a registered theme name is treated as a description and sent to the model, which writes a fresh theme for it. Doing so costs an extra model call and the result varies between runs, so use a registered name when you want the same look every time. vw.themes() lists the names that resolve without a model call, and a built-in name works even with no API key set. Writing your own theme theme = vw.theme(&quot;like national geographic but greener&quot;) print(theme.description) vw.create(&quot;...&quot;, df, theme=theme) Pass the Theme object itself rather than theme.description. A description string is not a registered name, so passing it sends you back through generation and produces a different theme. To reuse a theme in later sessions, give it a name: theme.save(&quot;nat_geo_green&quot;) vw.create(&quot;...&quot;, df, theme=&quot;nat_geo_green&quot;) Theme.save writes a JSON file named after the theme into .vibewidget/themes/ in your project and registers the name for the rest of the session. Because the file sits in the project, it can be committed and shared with the repository. Themes saved by older versions under ~/.vibewidgets/themes/ are still read. Keeping a look across edits An edit reuses the theme of the widget it came from, so the visual language stays the same while you change behavior or layout. Widget PreviewOpen the live docs to see this interactive widget. v1 = vw.create(&quot;basic scatter&quot;, df, theme=&quot;financial_times&quot;) Widget PreviewOpen the live docs to see this interactive widget. v2 = v1.edit(&quot;add hover tooltips and a right-side legend&quot;) To change the look on an edit, name a different theme: v3 = v2.edit(&quot;soften the palette and reduce gridlines&quot;, theme=&quot;minimal&quot;)
